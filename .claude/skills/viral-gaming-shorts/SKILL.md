# Viral Gaming Shorts Producer

Turn footage the user owns or is authorized to edit into finished, truthful YouTube Shorts. When asked to make videos, render the requested clips rather than stopping at an edit plan, if media and tools are available. Never claim an asset or check exists unless it was actually produced or run.

## Non-negotiable safeguards

- Use only user-provided or otherwise authorized media and permitted access methods. Never bypass DRM, paywalls, access controls, or platform restrictions. Public availability is not permission to reuse. If a link is inaccessible, request an upload; distinguish live footage, replay/VOD, direct media, and transcript-only input. State the reviewed interval for partial live footage.
- Preserve the source's meaning. Do not invent speech, events, or context; verify captions against audio and mark uncertain words with timestamps. Respect privacy. Do not promise virality or mislead with hooks or titles.
- Music must be provided by the user or licensed for the intended use. Do not rip game soundtracks. Report track, source, usage basis, and attribution. If clearance is unavailable, omit music; when appropriate provide a clean export and explain how to add a cleared track in YouTube.

## Produce the Shorts

1. **Inspect first.** Review repository instructions and available tools; use `tools/shorts_media.py` when available (see [WORKFLOW.md](WORKFLOW.md)). Inspect source duration, dimensions, rotation, frame rate, audio streams, and decodeability. Identify the intended mic/game mix. Some files have a single mix; others have a mix plus stems. Never add a full mix to its stems. Confirm the selected stream is audible; never trust the first audio stream by default. Keep source files untouched.
2. **Find moments.** For long footage, scan manageable overlapping chunks, then inspect likely moments with lead-in and aftermath. Use verified transcript, game sounds, reactions, and visible events; loudness alone is weak evidence. Include quiet visual payoffs. Note source in/out, what actually happens, and rationale. Rank by fast comprehension, clear payoff, and distinctness; merge duplicate overlapping moments. If choices are clear, proceed to render without asking the user to select. Deliver fewer than requested only if footage has fewer distinct moments.
3. **Edit for a natural payoff.** Default to 1080×1920, H.264/AAC, original-language captions, and approximately 20–45 seconds per Short. Duration is an editorial target, not a hard trim: preserve natural setup and ending. Use a truthful immediate hook, essential context, action, payoff, and clean ending. Make cuts on the edited timeline and preserve audio sync.
4. **Compose facecam over gameplay.** Inspect representative frames near the beginning, middle, and end of each selection. Locate the real webcam panel; don't mistake game portraits, characters, or HUD for a facecam. Prefer a stable panel crop over jittery tracking. Start with webcam about the top third and gameplay the lower two-thirds. Keep full head and natural headroom. Fit gameplay first, preserving aspect ratio, action and UI; use neutral/blurred padding as needed. Never stretch or zoom excessively. Favor a wider crop if a tighter one loses the crosshair, subtitles, scoreboard, minimap, or payoff. A baked-in webcam must not be duplicated if it can be avoided without losing essential action. If webcam is absent/unreliable, make gameplay-only; don't hallucinate one. If it moves/disappears, use the stable region only while valid or switch layout. Offer a source-pixel webcam-region override for difficult layouts (x,y,width,height, origin upper-left); document the chosen coordinates. Use helper `--webcam x,y,w,h` and `--game x,y,w,h` overrides where applicable.
5. **Audio matters.** Explicitly map the intended audio stream. Keep streamer voice and meaningful game sounds intelligible; preserve intentional quiet. Use a single full mix OR selected mic/game stems, not both. Mix/duck music conservatively only when cleared. After rendering, decode the MP4 and compare multiple known-audible source moments with corresponding output moments, including speech and a game cue if available. Check for absent/silent audio, clipping, and sync drift. If expected audio is missing, fix mapping/mix and rerender. If source is silent, disclose that.
6. **Captions on final timeline.** Transcribe the actual audio or use a verified transcript. After cuts, transcribe the final dialogue or remap cues through the edit decision list; use the same verified cues for burned captions and UTF-8 SRT sidecar with timecodes relative to the exported clip. Use readable high-contrast one/two-line phrases, natural breaks, and placement clear of face, HUD, and platform controls. Check the first cue, one after an internal cut, and final cue against rendered video. Flag uncertain words and exact timestamps. If speech cannot be verified, explain. For speech-free visual highlights, preserve game audio and omit dialogue captions.
7. **Verify and recover.** Render to a temporary path; only promote it to a final readable unique filename after decode and checks pass. Never leave failed output named as finished. For batch runs, retain successful clips and report each failed clip and cause. Verify dimensions, duration, playback/decode, framing, caption timing, audio, music rights, and clean start/end. Use repository tools and FFmpeg helper where possible; if unavailable, say what blocked rendering and ask for an upload/tool rather than pretending.

## Delivery

For each finished Short, provide the MP4 and SRT when applicable, plus a concise report: source timecodes; final duration; moment and selection rationale; layout and webcam coordinates or gameplay-only reason; audio stream/mix and checks; music/rights or omission; exact files and formats; remaining review items; and one accurate suggested title. Clearly separate actual finished assets from recommendations. See [WORKFLOW.md](WORKFLOW.md) for helper commands, coordinate example, caption/audio behavior, and limitations.
